# Baseline: reader vs. Canvas website (2026-10-20)

Milestone 3 measurement of the selected workflow, run back to back on the same account, data, machine and connection:

> start → course list → GPU Computing assignments → Lab-2 assignment → back to the list

Bottom line: once you act, the reader shows fresh data in **0.27–0.33 s**, where the website takes **2.1–2.7 s**. That's about 6–10× faster, with **one request of 2–21 KB per screen** instead of 130–190 requests. A saved copy is on screen in about **1 ms**.

Almost all of the reader's time is Canvas's network response; its own work (parsing, updating, drawing) takes 1–3 ms. These are 10 runs from one evening on one home connection: good for medians and ranges, not for tail latency.

## Setup

| | |
| --- | --- |
| Machine | AMD Ryzen 7 4800H, 15 GB RAM, Windows 11 Home, home network |
| Time | 2026-10-20, 16:27–16:33 EDT, all runs within six minutes |
| Account / data | One student account, 17 active courses; GPU Computing has 4 assignments; Lab-2 has a 411-character description |
| Reader | Release build, commit "Add timing instrumentation and benchmarks"; `tuicanvas --bench 10` and `--bench 5 --terminal` |
| Website | Microsoft Edge 155.0.4283.62, headless, 1366×800, via `python -m tools.browser_bench --runs 10`, with the same saved session |

### What "done" means

| | Website | Reader |
| --- | --- | --- |
| Start of timing | Navigation start (the page's own clock) | The key press (process start for the first screen) |
| Course list / dashboard | Link to the selected course visible | Course list drawn with data from Canvas |
| Assignment list | Link to Lab-2 visible | List drawn with data from Canvas |
| Assignment | First words of the description visible | Detail drawn with data from Canvas |
| How it's detected | Checked inside the page every animation frame; text inside scripts doesn't count | Timestamp after the frame is drawn |

Both sides measure fresh data from Canvas. The reader's saved copy appears much earlier and is reported separately ("first frame").

### Conditions

- **Website, warm cache:** the browser kept its HTTP cache and connections from earlier runs; one unrecorded warm-up first.
- **Website, cache disabled:** DevTools-style "disable cache" for the whole run, but with open connections and signed in.
- **Reader, cold:** new process state for every run (new connection pool, so a fresh TLS handshake; no saved copies). Timing starts before the HTTPS client and runtime are created.
- **Reader, warm:** one long-lived client with saved copies present; one unrecorded warm-up first.
- The reader drew either to an in-memory screen (110×34, 10 runs per condition) or to a real console window (5 runs per condition) to include terminal output.

## Results

### Time to fresh content: median [min–max], ms

| Step | Website, warm cache | Website, cache disabled | Reader, cold | Reader, warm |
| --- | ---: | ---: | ---: | ---: |
| Dashboard / course list | 2722 [2435–3052] | 2477 [2015–3143] | 420 [319–452] | 306 [267–448] |
| Assignment list | 2107 [1707–2299] | 2216 [1924–3175] | 336 [223–421] | 327 [231–367] |
| Assignment page | 2639 [2310–2938] | 2968 [2416–5277] | 283 [229–504] | 271 [228–378] |
| Back to the list | not measured (a fresh page load like the list) | | 273 [235–393] | 282 [248–475] |

The reader's cold "course list" includes creating the runtime, the HTTPS client and a new TLS connection; the 6 ms to decrypt the session comes on top. The website's dashboard does more than the course list (cards, to-do list, announcements), so that row is the least like-for-like.

### Where the time goes (website, warm cache, median)

| Page | HTML received | DOMContentLoaded | Content visible | load event |
| --- | ---: | ---: | ---: | ---: |
| Dashboard | 682 ms | 1288 ms | 2722 ms | 3009 ms |
| Assignment list | 714 ms | 1268 ms | 2107 ms | 2276 ms |
| Assignment page | 780 ms | 1283 ms | 2639 ms | 2138 ms |

The server-rendered HTML alone takes 0.7–0.8 s, longer than a whole reader step. The content then appears 1.3–1.9 s later, after the page's scripts load and fetch the data.

### Where the time goes (reader, warm, median)

| Step | Saved copy on screen | Network | Parse | Response → fresh frame |
| --- | ---: | ---: | ---: | ---: |
| Course list | 1.2 ms | 295 ms | 0.2 ms | 0.8 ms |
| Assignment list | 1.0 ms | 315 ms | 0.1 ms | 0.6 ms |
| Assignment | 1.5 ms | 261 ms | 0.1 ms | 0.8 ms |
| Back to the list | 0.4 ms | 268 ms | 0.1 ms | 0.6 ms |

In warm runs all 10 first frames already showed content (the saved copy). In cold runs only "back to the list" did, because the list had just been loaded.

### Requests and data per step (median)

| Step | Website requests (to content / total) | Website transferred, warm / cache disabled | Reader requests | Reader data |
| --- | ---: | ---: | ---: | ---: |
| Dashboard / course list | 144 / 175 | 2.0 MB / 6.6 MB | 1 | 21.2 KB |
| Assignment list | 133 / 156 | 70 KB / 4.4 MB | 1 | 1.9 KB |
| Assignment page | 193 / 197 | 76 KB / 5.9 MB | 1 | 4.5 KB |

Website bytes are bytes transferred (compressed; cached responses count as zero). Reader bytes are decompressed JSON, so the comparison favours the website. 1 KB = 1024 bytes, 1 MB = 1024 KB.

### Reader resource use

- **In-memory runs:** 16.3 MB peak memory, 1.48 s CPU for the whole benchmark (21 workflow runs, 84 reads).
- **Real-console runs:** 15.9 MB peak, 0.80 s CPU (11 runs, 44 reads). About 18 ms of CPU per read, mostly TLS and HTTP.

Browser CPU and memory were not measured.

| Local key → frame | ≤ 16 ms | Selection move: 0.3–0.4 ms in memory, 0.9 ms median (1.3 ms max) on a real console | Met |

## Limits of this baseline

- **One machine, one connection, one evening, 10 runs.** Network times vary with time of day; repeat before quoting tail figures.
- **The browser ran headless.** A visible window adds compositing and painting, so real browsing is probably no faster than this.
- **Completion is checked differently on each side,** as described in the "done" table. It's the same information, but the website's dashboard shows more than the course list.
- **Only part of the reader's terminal cost is covered.** The real-console runs used the default console host; output to other terminals (Windows Terminal with GPU text rendering, Git Bash) was not measured separately.
- **The website runs that bypass the cache keep connections and sign-in,** so they aren't a "first visit".

## Reproducing

```powershell
target\release\tuicanvas.exe --bench 10                     # reader, in-memory screen
target\release\tuicanvas.exe --bench 5 --terminal           # reader, real console
.venv\Scripts\python.exe -m tools.browser_bench --runs 10   # website
```

Each writes a metadata-only JSON report to `benchmarks/private/`: timings, counts and sizes, with no content, URLs or cookies. During normal use, `tuicanvas --diag` logs the same timings for every key press and read to `%LOCALAPPDATA%\TUICanvas\diagnostics.jsonl`.
